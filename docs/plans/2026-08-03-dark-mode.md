# Day/night (dark) mode

## Source notes
> Mode jour / nuit — idea, dropped from /dev/notes

## Problem / request
A dark theme toggle for the whole site. The note itself is terse but the ask is a well-understood, standard pattern: no further clarification needed to plan it, though the actual build is a bigger lift than the note suggests — see risks below.

## Proposed approach
1. **Theming foundation**: `apps/web/app/globals.css` currently defines exactly three CSS custom properties (`--background`, `--foreground`, `--accent`) — good, that's the right mechanism to extend. Add a dark variant block using Tailwind 4's `@custom-variant dark (&:where(.dark, .dark *))` (or `prefers-color-scheme` media query if going system-only first) redefining those three variables, e.g. `--background: #17141c; --foreground: #f2f0f5;`.
2. **Toggle + persistence**: add a small client component (e.g. `apps/web/components/ThemeToggle.tsx`) that reads/writes a `theme` value in `localStorage`, defaults to the OS `prefers-color-scheme`, and toggles the `dark` class on `<html>`. Place the toggle in `SiteHeader.tsx`. Set the class before first paint (inline script in `app/layout.tsx`'s `<head>`, not a `useEffect`) to avoid a flash of the wrong theme.
3. **Component audit (the real work)**: most components today hardcode light-mode-only utility classes directly — `bg-white`, `text-black/70`, `ring-black/10`, etc. — rather than routing through the CSS variables. A correct dark mode means auditing every component that uses these literal colors (cards across `/shows`, `/communaute`, `/mon-espace`, `/salle`, `/artiste`, the auth pages, `DevFeedback`, `ShareButtons`, etc.) and adding `dark:` variants (e.g. `dark:bg-black/40 dark:text-white/80`) or switching them to CSS-variable-backed utilities. This is the bulk of the effort, not the toggle itself.
4. Roll out in two passes to keep this reviewable: (a) toggle + root variables + top-level layout/header/nav, (b) per-page component audit, page by page, starting with `/shows` and `/mon-espace` (highest traffic).

## Out of scope
- Per-user theme preference stored server-side (localStorage is enough for v1).
- Automatic scheduling (e.g. dark mode only at night) — user- or system-driven only.

## Open questions / risks
- This is meaningfully bigger than "add a toggle" because color values are hardcoded across most components instead of centralized — flag the two-pass rollout to Théo so a first PR (toggle + shell) doesn't silently leave every page still white in dark mode.
- Decide whether `leaflet`/`react-leaflet` map tiles (used in `VenueMap.tsx`) need a dark tile layer too, or if it's acceptable for the map to stay light-themed inside a dark page.
